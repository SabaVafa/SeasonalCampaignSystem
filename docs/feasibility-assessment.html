Verdict: highly feasible — this is a well-shaped prototype, not a fantasy. Roughly 80% of the surface is standard e-commerce merchandising and CMS work, and the hardest-to-get-right part — the resolution engine — is already production-shaped: it is pure, dependency-free, and takes an explicit resolveActiveCampaign(campaigns, date) date argument instead of reaching for Date.now(). That one seam is exactly where a real backend plugs in.

The real cost and risk live in three integration surfaces: a scheduled campaign backend to replace the localStorage store; wiring discountRule into the shop's actual pricing/promotion engine; and caching so the resolved campaign is served fast and flipped on schedule. Only one of these — discount & price integrity — is genuinely hard and legally non-negotiable for a German shop. The target platform has since been confirmed as JTL-Shop 5 (OnPage Composer in use), which supplies all three natively — the companion JTL blueprint maps every feature onto it.

B

The three integration challenges

Everything marked Integration or Hard collapses into three problems. Solve these and the rest is assembly.

01

Scheduled campaign backend

Integration

The engine and data model are ready; the store is the gap. localStorage becomes a content service (headless CMS or a campaign table) with draft → scheduled → published states. Resolution moves server- or edge-side so the public page is computed once and cached.

What it takes
  • A campaign content type mirroring the current schema — the schema is already the hard-won part.
  • Resolution as a shared service the storefront and admin table both call with an explicit date.
  • Scheduling that flips state at the window boundary in Europe/Berlin, with cache invalidation on the flip.
02

Discount & price integrity

Hard

This is the one that must be right. Displaying "−25%" is easy; guaranteeing the cart and checkout charge −25%, VAT-correct, for the right customer group and country, is a promotion-engine problem. In Germany it is also a legal one — a struck price must reference the correct baseline (PAngV / lowest price in the last 30 days).

discountRule{ type, value, scope } should not compute prices in the front end at all. It should map to a rule the platform's pricing/promotion engine owns, and the storefront reads the resulting price so badge and cart can never disagree.

What it takes
  • Translate each discountRule into a native promotion (cart price rule / voucher / bundle) in the commerce platform.
  • Badge, PDP price and cart all read one source of truth — the priced line item, never a recomputed guess.
  • PAngV-compliant reference pricing carried through the discount UI.
03

Caching & CDN

Integration

A live shop caches aggressively. Public traffic wants the resolved campaign baked into an edge-cached page — the cache key includes the resolved campaign id, and the cache is invalidated the moment a window opens or closes.

The work is getting that invalidation right, so a scheduled campaign appears within seconds of its start rather than on TTL expiry, and the evergreen fallback stays the always-cacheable default.

What it takes
  • Edge cache keyed on resolved-campaign + customer group + locale.
  • Scheduled-flip cache purge so a new campaign appears within seconds, not on TTL expiry.
  • The evergreen fallback as the always-cacheable baseline when nothing is active.
C

Risks & honest caveats

Struck-price law (PAngV) legal

A German shop showing a reduced price must display the lowest price of the prior 30 days as the reference. The discount UI must carry this figure, not just the percentage.

Timezone & DST on recurring windows edge

"Starts 24.11" means local midnight Europe/Berlin. The year-wrap and DST transitions are the spots to test — resolve in one canonical zone, not the visitor's.

Concurrency & approval process

Two editors, overlapping windows, a mistimed publish. The overlap warning is a good start; production needs a review gate and an audit trail.

Client-side injection & CLS perf

Injecting hero/promo after load shifts layout and hurts SEO. Move campaign slots into server-rendered templates for the live site.
