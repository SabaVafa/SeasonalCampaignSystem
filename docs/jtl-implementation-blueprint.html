Implementation Blueprint · JTL-Shop 5

Seasonal Campaigns as a JTL-Shop Plugin

How to make the campaign prototype fully implementable on JTL-Shop — by mapping every feature onto native JTL machinery (Aktionen, Sonderpreise, Wawi, Portlets, plugin hooks) and keeping the plugin a thin presentation-and-scheduling layer that never touches pricing.

Target: JTL-Shop 5.x (PHP 8 · Smarty · Snackys base + ETK2022 child template · OnPage Composer) + JTL-Wawi as master data · shop: edelstahl-tuerklingel.de — stack confirmed against the live site

The core decision: separate presentation from pricing. The plugin owns campaign scheduling, resolution and presentation. Prices, discounts, VAT and stock stay entirely inside JTL/Wawi. A campaign references a JTL promotion rather than computing one — so the badge on the card and the price in the cart can never disagree, and everything stays PAngV-compliant and customer-group correct out of the box.

This turns the assessment's hard items green: discount enforcement becomes a native Aktion/Sonderpreis and price & VAT come from the shop's price calc. What remains for the plugin is exactly the part JTL doesn't already do: knowing which campaign is live today, and dressing the page for it.

A

Four principles the build rests on

Principle 01

Plugin presents, JTL prices

The resolution engine and templates live in the plugin. Every euro is calculated by JTL's price engine against Wawi data. The plugin reads the priced line item — it never multiplies by 1.19.

Principle 02

Wawi is the source of truth

Products, prices, VAT, customer groups, stock and promotions are authored in Wawi and synced to the shop. The plugin adds only campaign metadata in its own tables — it never writes prices the sync would overwrite.

Principle 03

Server-rendered, then enhanced

Hero, promo strip and product slots render in Smarty via OPC Portlets & template hooks — good for SEO and CLS. JS only enhances (countdown, the premium dropdowns) on top of the Bootstrap 4 + jQuery the shop already ships, never injects the campaign after load.

Principle 04

Resolve once, cache hard

The active campaign is resolved per request but cached with JTL's object cache, keyed on campaign + customer group + language, and flushed the moment a window opens or closes.

E

The discount bridge (do this right)

Single most important integration

A campaign never sets a price. It points at a JTL promotion.

Authoring flow: a merchandiser creates the Aktion / Sonderpreis in Wawi (percent or fixed, date range, target category, customer groups) — that is the legally-binding, checkout-enforced discount. In the campaign plugin they then create the matching campaign (hero, badge text, template, window) and select that Aktion in an aktion_ref dropdown.

Result: the plugin schedules and dresses the presentation; JTL owns the money. No front-end price math, no divergence between badge and cart, PAngV reference pricing inherited for free. Optionally the plugin can align the two date windows on save so they can't drift apart.

G

Making the prototype code carry over

Engine → PHP, near line-for-line. campaign-engine.js is pure and dependency-free; resolveActiveCampaign, priority sort, month/day wrap and the disabled gate port directly to CampaignResolver.php and keep their unit tests.
Data model → migration columns. The seed JSON fields map 1:1 to table columns; discountRule is replaced by an aktion_ref foreign key into JTL's promotion, not stored math.
Admin UI → backend tab, mostly as-is. The authored HTML/CSS/JS (premium dropdowns, table, overlap warning) drops into the admin tab; only the localStorage store swaps for AJAX calls to the plugin controller.
Storefront markup → Smarty templates. The hero/promo/countdown/card markup becomes .tpl partials fed by Smarty assigns; the design-system CSS ships with the plugin.
H

JTL-specific risks

Don't fight the Wawi sync

Never write article prices from the plugin — Wawi will overwrite them on the next sync. Only ever reference an Aktion/Sonderpreis; keep plugin tables to presentation + scheduling.

Template updates

Ship templates inside the plugin (or the ETK2022 child template), never by editing Snackys directly, so a template update doesn't clobber the campaign markup.

Cache correctness

A campaign that flips at midnight must purge the object cache at the boundary; a stale cache is the classic "the sale didn't start" ticket.

Migration discipline

All schema changes via versioned Migration classes with working down(), so install / update / uninstall stay clean across shop versions.
